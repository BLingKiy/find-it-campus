## 1. 4.1 真实接口回归 —— 「提交 → 列表 → 详情」是否真的落库

**结论：通过（10/10 项检查）。**

### 1.1 为什么需要单独复验

4.1 交付时前端用 `VITE_USE_MOCK=true` + sessionStorage 演示：界面能跑通三个页面，但数据没有进 MySQL。
「页面能显示」与「数据真的写进库」是两件事，这条残留要补的正是后者。

### 1.2 做法

1. `web/.env.local` 设 `VITE_USE_MOCK=false`（不提交，`.gitignore` 已忽略），前端 5173 → Vite 代理 → 后端 18080；
2. Playwright 在真实页面上填表提交（`E2E-C-01`），断言跳转到详情并出现「发布成功」；
3. 回列表断言新记录排在首位（`E2E-C-02`），再用关键词检索到它（`E2E-C-03`）；
4. **换一个全新的浏览器上下文**直接打开该记录 URL（`E2E-C-04`）：
   没有 sessionStorage、没有上一页的内存状态，页面依然渲染完整内容，并确实发出 `GET /api/records/:id`；
5. 最后直连 MySQL 查这一行，逐字段比对（`qa/db/evidence.mjs`）。

### 2.3 需要注意的两处「看起来不一致、实际是设计」

1. **卡片 16px vs 面板 20px**：基线只要求「同类元素同值」，卡片用 `--sp-4`、面板用 `--sp-5`，
   三页各自一致；这不是跨页漂移。
2. **详情页没有表单控件**：`CON-03` 只覆盖列表筛选区与提交表单两页，详情页本来就没有 `.control`；
   把它算作「缺失」会制造假失败，所以按页面职责分开判。
3. **提交页按钮 44px / 其余 40px**：提交页用的是 `.btn--lg`（主操作强调），
   与列表页 40px 的 `--btn-h` 属同一尺寸体系的两档，圆角与配色仍是同值。
