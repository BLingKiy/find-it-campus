## 2. 「真的走了真实接口」怎么证明

不是靠 `VITE_USE_MOCK=false` 一行配置自证，而是三件事同时成立：

1. **网络层**：Playwright 监听请求，列表页发出的请求形如
   `http://localhost:5173/api/records?status=PENDING&page=1&pageSize=10`，
   响应 `total=21`、`list[0].id=26`；关键词筛选时为 `/api/records?status=PENDING&keyword=%E9%92%B1%E5%8C%85` → `total=2`。
2. **数据层**：E2E 通过 UI 提交的记录（本轮 id 见 `qa/reports/e2e-created.json`）能在 MySQL 里查到整行，
   且标题、分类、联系方式、联系人、描述长度逐项一致 —— 详见 [阶段 4 复验 §1](./5.1-stage4-recheck.md)。
3. **失败注入层**：异常路径用 Playwright 的 `route.abort / route.fulfill` 在**网络层**制造
   「连接被拒 / 404 / 500 / 503」，页面必须走自己的错误处理；如果前端还留着 mock 分支，这些注入不会影响渲染，断言就会露馅。

## 3. 本轮走查发现的问题

| 编号 | 现象 | 定位 |
|---|---|---|
| DEF-02 | 「重置筛选」后 URL 仍带旧参数，刷新/分享后筛选重现 | `web/src/composables/useRouteQueryState.ts` 写回 URL 时用 merge，默认值被 prune 但旧键没删 |
| DEF-03（P3） | 匹配区 503 时文案重复：「匹配服务暂不可用 匹配服务暂不可用，请稍后再试」 | `MatchPanel` 的 `title` 与 `describeError()` 返回同一句 |

两条都不影响主流程可用性，详见 [缺陷清单](./5.1-defects.md)。

## 5. 选择器与可维护性说明

项目当前**没有 `data-testid`**，本轮选择器按「语义角色 → 可见文本 → 组件类名」的优先级取：
`getByRole('button', { name: '提交启事' })`、`#filter-keyword`（label 已配对 `for`）、
`.record-card` / `.match-panel__list li`（类名兜底）。

后果是：改按钮文案或卡片类名会让用例失败。这类失败是「测试维护成本」，不是产品回归。
建议后续（不属 5.1，交 4.x 或 6.x）给三页关键节点补 `data-testid`：
列表卡片、分页、提交按钮、表单字段、匹配结果项、空态/错误态容器。
