# /api/match 匹配效果评估（ZHYYKFX-10 · 5.1）

> 目标不是证明「效果不错」，而是给出**可复核的命中与失败**：每条样例有输入、期望、实际、判定，
> 指标可重跑，失效场景有边界。

- 引擎：`LOCAL_KEYWORD`（`impl` 分组；契约 §8.4 要求不同实现不混池，本轮只有这一种）
- 参数：`topN=5`、`minScore=0.3`、`occurredAt` 与 `createdAt` 走 seed 数据
- 样例来源：`db/seed.sql` 文末 3.2 预置的 S1–S6 / N1–N4
- 复现：`node qa/match/evaluate.mjs`（生成 `qa/reports/match-eval.md` 与 `.json`）
- 生成数据来自 2026-10-22 本机实跑，不是估算

## 1. 两个协议（为什么不只跑一遍）

样例集里没有写死 `type` 参数，但契约 §8.1 的 `type` 语义是「我要找的记录类型」。所以同一条样例换个 `type` 会有不同的正确 top1：

- **P1 产品路径**：按详情页真实调用方式带 `type`（失主找招领帖 → `FOUND`；拾到者找失物帖 → `LOST`）。
  页面 `MatchPanel` 传的 `wantType` 就是 `record.type === 'LOST' ? 'FOUND' : 'LOST'`。
- **P2 不限类型**：完全不带 `type`，观察原始召回，用于解释「不带方向过滤会怎样」。

两组分开统计，不混池。

**怎么读这 4 条「不通过」**：2/14、3/15、4/16、6/18 是同一件事的两侧（一个丢了、一个捡到），
不带 `type` 时「同事件的另一侧」天然更容易命中——它不是误报，是**缺方向约束时的排序歧义**。
证据是 top3 命中率：两种协议都是 **10/10**，期望的那条始终在前三。
产品路径（P1）永远带 `type`，所以这个歧义不会出现在真实界面上。

## 4. 指标

| 指标 | P1 产品路径 | P2 不限类型 |
|---|---|---|
| top1 命中率 | 10/10（100%） | 6/10（60%） |
| top3 命中率 | 10/10（100%） | 10/10（100%） |
| 明显误报（score≥0.6 且不相关） | 0 | 0 |
| 两次调用结果完全一致 | 10/10 | 10/10 |
| 后端 `tookMs`（只计引擎）avg / p95 / max | 0 / 0 / 0 ms | 0.2 / 1 / 1 ms |
| 客户端端到端 avg / p95 / max | 128.9 / 368.2 / 368.2 ms | 89.2 / 366.3 / 366.3 ms |

两条耗时读法的差异必须说清，否则会得出错误结论：

- `tookMs` 是后端**只包住引擎调用**的整数毫秒，首次调用做过类目词表加载（实测约 19ms），之后多为 0–1ms；
- 客户端端到端包含 Node→本机→HTTP→序列化，且 `localhost` 在本机会先走 IPv6 再回退，实测有 300–700ms 的抖动；
- 所以这组数字**不是性能结论**，只说明「引擎本身很轻」。真正的延迟归因见观察项 OBS-01。

## 5. 确定性（flaky 的常见来源）

同一输入连续两次调用，`(recordId, score)` 序列 10/10 完全一致，且两次各自产生独立快照（`matchId` 不同）。
这依赖契约 §8.4 的「同分按 recordId 升序」，本轮没有出现同分，但排序实现存在，属于结构上可复现。

## 6. 失效场景抽样（不进入正式判定，只标边界）

额外抽了 4 条样本集之外的输入，用来确认「本地关键词」的边界在哪里（引擎文档 §3.1 已声明同类限制）：

| 输入 | 结果 | 说明 |
|---|---|---|
| `丢了一个水杯` | 空结果 | 库里有「不锈钢保温杯」（9 号）。「水杯」与「保温杯」没有共同 bigram，单字权重不足以过 0.3 阈值 |
| `丢了airpods右耳` | 5@0.53 | 库里的「蓝牙耳机连充电盒一起丢了」被召回——靠的是「充电/耳」等弱重合，不是真正识别了同义词 |
| `图书馆丢了黑色钱保` | 1@0.84（正确 top1） | 错别字没毁掉结果，因为地点与颜色词仍在；但这是「错得不够狠」，不代表容错 |
| `tushuguan diu le qianbao` | 空结果 | 拼音/英文输入不支持 |

结论：当前实现对**具体名词 + 地点/颜色描述**有效，对**同义词、拼音、脱离词表的近义表达**无效。
这不是缺陷（3.2 交付时就写明这是选择「零外部依赖、可复现」的代价），但答辩时不能把它讲成语义理解；
需要泛化时按 `docs/ai-match-module.md` §3.2 换实现，接口与前端不动。

## 7. 可复现的判定脚本

```bash
node qa/match/evaluate.mjs   # 输出 qa/reports/match-eval.md 与 match-eval.json
```

脚本里的判定函数 `judge()` 就是上面三条口径的实现：`top1 命中`、`mustExclude`、`score≥0.6 且不在相关集`。
改样例只改 `SAMPLES` 数组，不用改判定逻辑。
