## 1 环境就位（每次重录都要重做一遍）

### 1.1 起库并重置到 seed 初态

```bash
cd <仓库根>

```

**成功的样子**（这几个数字是后面所有讲解词的基础，差一个就全部作废）：

```bash
mysql -u root -N -e "USE find_it_campus; \
SELECT 't_user',COUNT(*) FROM t_user UNION ALL SELECT 't_category',COUNT(*) FROM t_category \
UNION ALL SELECT 't_record',COUNT(*) FROM t_record UNION ALL SELECT 't_match_result',COUNT(*) FROM t_match_result \
UNION ALL SELECT 't_pair_score',COUNT(*) FROM t_pair_score UNION ALL SELECT 't_notification',COUNT(*) FROM t_notification \
UNION ALL SELECT 't_access_log',COUNT(*) FROM t_access_log UNION ALL SELECT 'PENDING',COUNT(*) FROM t_record WHERE status='PENDING';"
# t_user        3
# t_category    9
# t_record      24
# t_match_result 0
# t_pair_score  14
# t_notification 8
# t_access_log  0
# PENDING       21
```

`t_access_log` 与 `t_match_result` 必须是 **0**：这两张表只由真实请求产生，seed 里没有假数据。
`PENDING=21` 决定列表页右下角的「共 21 条」；另外 3 条是 23/25 两条 `COMPLETED` 和 24 一条 `CLOSED`，默认不出现在公共列表。

## 3 逐段脚本

### S0 · 环境就位（0:30）

**画面**：左 1/3 终端（`mysql>` 与后端日志），右 2/3 Edge 正常窗口 + InPrivate 窗口并排。

**操作**：
1. 终端执行 `curl -s http://localhost:18080/api/health`，让返回值停在屏幕上；
2. 正常窗口打开 `http://localhost:5173/`；InPrivate 窗口也打开同一地址（右上角能看到「InPrivate」标识）。

**预期画面**：health 的 JSON 四个键齐全（`status:UP` / `db:UP` / `version` / `engine:local`）；两个窗口都是列表页。

**讲解词**：
> 环境自证一下。`db` 是 `UP`，后端真连着 MySQL；`engine` 是 `local`，装配的是本地关键词引擎。
> 右边两个窗口是**两个独立浏览器上下文**：一个正常窗口登 demo01，一个 InPrivate 登 demo02，
> 因为 v2 的会话是 `HttpOnly` 的 `JSESSIONID` Cookie，同一个 Profile 里两个标签页共用一个会话，换不了身份。

**易错点**：`db` 显示 `DOWN` 说明库没起，列表会空着 —— 不要硬录。

### S1 · 匿名基线：遮蔽视图 + 登录守卫（0:35）

**画面**：正常窗口（匿名）。

**操作**：
1. 地址栏输入 `http://localhost:5173/records/13`，等卡片渲染；
2. 鼠标依次划过「联系方式」「联系人」「详细描述」三处；
3. 滚到顶栏，点「发布启事」——**让它跳**；
4. 停在登录页，让观众看到地址栏 `?redirect=/records/new` 和页顶那条提示。

**预期画面**：

- 页顶蓝色横幅：**「你正在匿名浏览」** +「登录后可管理你发布的启事，并在配对确认后查看对方联系方式。」+ 一个「去登录」按钮；
- 「联系方式」不是号码，是占位说明「联系方式仅发布者本人及已确认配对的对方可见」，旁边一个「查看联系方式」按钮；
- 「联系人」显示 **`周**`**（库里是「周同学」）；
- 「地点」显示 `图书馆三楼自习区`（正好 8 个码点、结尾不是定位片段，所以**原样**）；
- 点「发布启事」后地址栏 = `/login?redirect=/records/new`，登录页顶部：**「请先登录 / 登录成功后会自动回到刚才访问的页面。」**

**讲解词**：
> 现在这个窗口是匿名的，没登录，但内容读得到 —— 读到的是一份**遮蔽视图**：
> `contact` 字段在服务端就没有出现（响应体里连这个键都没有，不是空串、也不是 `138****5678` 这种部分可见）；
> 联系人「周同学」只留首字变成「周**」；描述和标题过四条打码规则。
> 遮蔽规则全仓库只有 `MaskingPolicy` 一个实现，列表、详情、`/api/match`、我的启事、通知五个出口共用它，
> 出口只决定「传不传原文」，不决定怎么掩。
> 然后我点「发布启事」：没登录的话，前端路由守卫直接把我送到登录页，并把原地址带在 `?redirect=` 上。

**易错点**：
- 如果联系人显示的是「周同学」全文，说明你其实已经登录了（顶栏右侧看一眼）。
- 「地点」这一格**刻意没被截断**，这是正确行为，不要当 bug 讲。要展示截断，加一句：`第三教学楼201` → `第三教学楼…`（实测在 `docs/testing/v2/C1-masking-evidence.md`）。

### S2 · 登录（0:55）

**画面**：正常窗口，停在登录页（S1 已经把它送上来了）。

**操作**：
1. F12 → Network，过滤框输入 `login`；
2. 学号输 `demo01`，密码**故意输错**一位，点「登录」；
3. 让红色横幅停 1 秒，在网络面板点开那条 `login`：Status `401`、响应体 `code:10006`；
4. 改成正确密码 `Demo@123456`，点「登录」；
5. 看网络面板那条 200 的 `login` → Headers → **Response Headers** 里的 `Set-Cookie: JSESSIONID=…; HttpOnly; SameSite=Lax; …`；
6. 页面自动回跳到「发布启事」，让观众看到地址栏从 `/login?redirect=…` 变成 `/records/new`；
7. 顶部导航点「启事列表」，让顶栏整条入镜：**启事列表 / 发布启事 / 通知（红点 5）/ 我的启事 / 学号 demo01 / 退出**。

**预期画面**：

- 失败：红色 alert 标题「登录失败」，文案 **「学号或密码不正确」**；HTTP `401` + `{"code":10006,…}`；
- 成功：HTTP `200` + `data:{studentNo:"demo01",displayName:"演示甲"}`，顶栏出现「通知」红点 **5**；
- 红点数字 5 来自 seed：demo01 名下 5 条未读（3 条 `PAIR_MATCH`、1 条 `PAIR_UNLOCK`、1 条 `SYSTEM`）。

**讲解词**：
> 这是唯一的登录入口：学号加密码，没有注册页、没有找回密码 —— 本期不做，写在已知限制里。
> 故意输错一次：返回 401、业务码 10006，文案是「学号或密码不正确」。这句话**刻意不分**「账号不存在」还是「密码错」，
> 免得这里变成账号枚举接口。
> 登对之后看响应头：`JSESSIONID`，`HttpOnly`、`SameSite=Lax`，会话在内存里，有效期 30 分钟。
> 注意它 `HttpOnly` —— 前端脚本读不到自己的会话标识，XSS 想带走会话也带不走。
> 顺带交代一句内存会话的代价：后端重启，所有人重新登录，这是限制第 3 条，S7 现场会让大家看到一次。
> 登录后顶栏多了三个入口：通知（红点 5）、我的启事、退出。红点的 5 是服务端 `unreadCount`，不是前端数的。

**易错点**：
- 「请先登录」那条蓝色提示只在被守卫送过来时出现，直接访问 `/login` 是没有的 —— 两种都正确，别现场解释半天。
- 别用 `demo02` 登正常窗口：S6 要在 InPrivate 里登 `demo02`。

### S3 · 发布（0:45）

**画面**：正常窗口 `/records/new`。

**操作**：
1. 类型选 **寻物**（radio `name="type"`，值 `LOST`）；
2. 标题：`图书馆三楼丢了黑色钱包（演示1028）`；
3. 描述（**整段照抄，里面刻意带一个手机号和一个 QQ 号**）：
   ```text
   2026 年 10 月 27 日下午，在图书馆三楼自习区靠窗座位旁的地上发现黑色皮质钱包不见了，里面有银行卡两张和现金若干，非常着急，捡到的同学联系我。联系电话 13800001234，也可以 QQ 联系 123456789。
   ```
4. 分类选「钱包卡证」；地点：`图书馆三楼自习区靠窗座位`；发生时间：`2026-10-27 16:30`；
5. 联系方式：`13800001234`；联系人：`演示甲`；
6. 点「提交启事」，等跳转；
7. 详情页停 2 秒，让「发布成功」提示与标题同框；
8. 鼠标划过「联系方式」那一格 —— **本人看到的是明文**。

**预期画面**：

- 跳转地址 `http://localhost:5173/records/27?created=1`（`27` 是干净 seed 之后的第一个自增值，**每重录一次都要重置库**，否则 28、29 往上走）；
- 绿色横幅「发布成功 / 这条启事已经出现在列表里了。」；
- 联系方式一格显示 `13800001234`，联系人显示 `演示甲`，描述里 `13800001234` 与 `123456789` **原样**（本人不遮蔽）；
- 底部状态区只有一行灰字提示：**「当前状态没有可执行的流转；「标记完成」需要已有双方确认的匹配（当前有效匹配 0 对）。」**
  —— 详情页不给「标记为已完成」按钮；「关闭启事」在「我的启事」的卡片上（两段式确认）。

**现场查库（终端 5 秒）**：

```sql
SELECT id, type, status, contact, publisher_name, publisher_id, pair_state
  FROM t_record WHERE id = 27\G
```

**预期输出**：`type=LOST`、`status=PENDING`、`contact=13800001234`（**明文**）、`publisher_name=演示甲`、
`publisher_id=1`、`pair_state=PENDING` 或 `SCORING`。

**讲解词**：
> 八个字段提交，落库了。这里最该看的是那行 SQL：**数据库里 `contact` 存的是明文**。
> 这是拍板过的取舍 —— 遮蔽只做在输出层，本人回显不需要反解，也不引入密钥管理；
> 代价是能读库的人看得到号码，靠部署侧访问控制兜底，这句话写在已知限制里。
> 为什么值得这样：一会儿 S5 用同一个 id 打开匿名视图，号码会**整个消失**，描述里的手机号会变成占位符。
> 再看底部那一行灰字：这条新记录现在**没有可执行的状态流转**，因为「标记完成」要求已经存在一条双方确认的配对，
> 这句话是后端算好了放进 `allowedStatuses` 的，前端不自己推流转规则。关闭入口在「我的启事」的卡片上，两段式确认。

**易错点**：
- 描述里的手机号 `13800001234` 是**假号**（seed 全用 138/139 段）。录之前说清楚，别让评委以为是真号。

### S4 · 打分：从「分析中」到出分（0:40）

**画面**：正常窗口 `/my`，「进行中」页签。

**操作**：
1. 顶栏点「我的启事」；
2. 第 1 张卡就是刚发的 27 号，状态徽标是 **`分析中`**，下面一行小字「匹配分析中，页面每 5 秒自动刷新；出分后会变成「N 条可能相关」。」；
3. **手离开鼠标**，等它自己变（最多等 2 个刷新周期）；
4. 变成 `N 条可能相关` 后，滚到顶栏，让未读红点入镜（**5 → 6**）；
5. 点「通知」，让最新一条停在屏幕上 2 秒。

**预期画面**：

- 卡片徽标从「分析中」变出来。**不设 Key 的环境里它变成 `已降级`**（不是「N 条可能相关」——这是正确行为，见 S7），
  同排还有一个黄色 `已降级` 小徽标，下面一条黄色 alert：**「已降级 / 智能匹配暂不可用，已用关键词匹配。分数仅供参考。」**；
  计数行给 **「其中 N 条可查看」「另有 N 条低分结果（仅计数）」**（具体数字以画面为准，别在讲解词里报死）；
  卡片下半区出现 `可能相关（N 条可查看）· 每对独立处理` 的配对列表。
- 顶栏红点 6；
- 通知列表第一条：标题 **「你发布的寻物启事有一条可能相关的招领」**，正文 **「相关度约 XX%，点击查看详情」**，右侧「未读」徽标 + 「标为已读」按钮；
- 页顶汇总一行：**未读 6 条 / 共 6 条**。

**现场查库**：

```sql
SELECT id, lost_id, found_id, score, engine, degraded_reason, status
  FROM t_pair_score WHERE lost_id = 27 ORDER BY score DESC LIMIT 5;
```

**预期输出**：至少一行 `lost_id=27`、`found_id=13`（就是那条「图书馆拾到黑色钱包」），分数最高的那行 `engine=LOCAL_KEYWORD`、
`degraded_reason=EMPTY_KEY`（当前无 Key），`status=NEW`。

**讲解词**：
> 发布接口不等打分。提交事务一提交，事件监听器把这对候选丢进线程池，`pair_state` 从 `PENDING` 走到 `SCORING` 再到出分。
> 「我的启事」页每 5 秒轮询一次，而且只在「进行中」页签、且确实有未出分的记录时才轮询 —— 不会挂在后台空跑。
> 出分的同时，双端各写一条 `PAIR_MATCH` 通知。这里有两个刻意的做法：
> 一、通知正文**不写对方标题**，只写「相关度约 XX%」——通知是长期留存的数据，把对方标题复制进来，等于给已关闭、已删除的记录留了一份不可回收的副本；
> 二、通知的唯一键是 `(user_id, pair_id, type)`，重放同一次打分不会产生第二条刷屏。
> 这张卡片现在写着「已降级」，这是这台机器没配密钥的正常结果，S7 专门讲它 —— 这里先不展开，一句带过。

**易错点**：
- **等不到出分**：看后端日志有没有 `PairScoringService` 的 WARN；或 `pair_state` 卡在 `SCORING`（进程被杀过会这样，10 分钟后由兜底扫描重算 —— 这段不要试图在录制里等）。
- 红点没变：`useNotificationBadge` 只在登录态变化与关键写操作后刷新，没刷新就手动刷新一次页面，别现场找补。

### S6 · 授权与撤回（1:00）

**画面**：左 = InPrivate（demo02），右 = 正常窗口（demo01），两边都停在记录 16 / 记录 4 的详情页。

**操作**：

2. InPrivate 的卡片上：`86%` + 「可能相关」+ 开关状态是 **`已公开我的联系方式`**（seed 里 `found_unlocked_at` 是 2 天前）；

4. **同步动作**：正常窗口（demo01）刷新 `/records/4` → 卡片提示变成 **「对方尚未公开」**，按钮变灰，**页面上原有的号码消失，没有残留**；
5. 在 demo01 的网络面板点开那条 `GET /api/pairs/4/contact`（若在撤回后点过一次按钮）：
   **HTTP 200**、`available:false`、`reason:"NOT_PUBLIC"`、`message:"对方尚未公开"` —— 响应体里没有号码；
6. InPrivate 里把开关**再打开**（PUBLISH），附言输入框填一句 `已公开联系方式，可直接联系`（≤200 字），保存；
7. demo01 侧刷新 → 提示回到「对方已公开联系方式」→ 点「查看联系方式」→ `13800000104` 回来。

**预期画面**：

- 撤回：`POST /api/pairs/4/contact-unlock {"action":"REVOKE"}` → `200` + `published:false` + `note:null`；
- 撤回后 demo01 侧：按钮禁用 + 「对方尚未公开」；审计多一行 `DENIED_NOT_PUBLIC`（**注意是 200 不是 403**）；
- 再公开：`published:true`、`unlockedAt` 变成刚刚；demo01 的红点**不会**因为这条再公开而增加（见易错点）。

**讲解词**：
> 这是 0.75 到 0.90 这一档的核心动作：授权，以及**撤回授权**。
> 左边是拾到东西的同学，右边是丢伞的同学，同一条配对的两端。左边把「公开我的联系方式」撤掉，
> 右边刷新之后提示立刻变成「对方尚未公开」，而且**页面上刚才那个号码没有了** —— 组件在收到 `available:false`
> 时会主动清掉本地已显示的号码，不留旧值。
> 这里有个细节值得说一句：撤回之后再取号，接口返回的是 **200**，`available:false`，业务上不叫错误。
> 「对方还没公开」是一个正常业务状态，给它 403 会让前端很难写。但审计照写一行 `DENIED_NOT_PUBLIC`。
> 再点一次公开，附言可以带一句话（上限 200 字，且会先把里面的号码打码再落库）。
> 撤回会把附言一起清空 —— 这是拍板过的口径，撤回同意不留残留。

**易错点**：
- **`PAIR_UNLOCK` 通知是幂等的，不会重复发**：唯一键 `(user_id, pair_id, type)`，而 seed 里 demo01 针对 pair 4 已经有一条 `PAIR_UNLOCK`（那条通知是这次演示的第 5 个红点）。所以「再公开」这一步**不会**让对端红点 +1。讲解词里别说「对方会收到通知」，要说「第一次公开会让对方收到一条通知，重复公开不刷屏」。
- 撤回与再公开之间，demo01 侧一定要**刷新**，不刷新看到的还是旧卡片（卡片状态是本地态，不推送）。这是 v2 的口径：不做服务端推送。
- 录完这一段，pair 4 的 `found_unlocked_at` 与通知表都和 seed 初态不同了。**重录 S5/S6 之前按 §1.1 重置库。**

**（可选 +35s，标记为 S6b）**：这里能把「**列表隐藏 ≠ 匹配隐藏 ≠ 详情可见**」三件事一次讲完。

1. demo01 打开 `http://localhost:5173/records/10`，底部 **「标记为已完成」是可点的**
   （这条有一个 0.95、双方已确认的配对 pair 12）；
2. 点下去 → 详情页立刻变成 **「记录不存在或不可查看」** 空态。**这不是 bug**：拍板口径是终态详情对所有人都 404，

### S7 · 降级演示（0:50）

**画面**：正常窗口 + 终端。

**操作**：

1. 直接回 S4 那条新记录（`/records/27` 本人详情，或 `/my` 的卡片）；
2. 让**「已降级」**徽标与横幅同框：卡片右上 `已降级`，面板顶部
   **「已降级 / 智能匹配暂不可用，已用关键词匹配。分数仅供参考。」**；
3. 终端跑：
   ```sql
   SELECT id, score, engine, degraded_reason, latency_ms, prompt_tokens, completion_tokens
     FROM t_pair_score WHERE lost_id = 27 ORDER BY score DESC LIMIT 1\G
   ```
   **预期输出**：`engine=LOCAL_KEYWORD`、`degraded_reason=EMPTY_KEY`、`latency_ms=NULL`、两个 tokens 列 `NULL`；
4. 讲一句「外部不可用的另外六种原因同样走这条路」（`UNAUTHORIZED` / `TIMEOUT` / `NON_JSON` /
   `SCORE_OUT_OF_RANGE` / `HTTP_ERROR` / `CIRCUIT_OPEN`，连续 5 次失败后熔断打开 5 分钟）；
5. **对照：另一条链路刻意不降级。** 停后端，换环境重启：
   ```bash
   FINDIT_MATCH_ENGINE=external ./mvnw spring-boot:run     # PowerShell: $env:FINDIT_MATCH_ENGINE='external'
   ```
   起来后 `curl -s http://localhost:18080/api/health` 让 `engine:"external"` 停在屏幕上；
6. 浏览器**会掉登录**（内存会话随进程没了）—— 顺手讲一句限制第 3 条，然后重新登 demo01；
7. 非本人的一条详情（`/records/13`）点「开始匹配」→ 匹配区红色错误横幅，HTTP `503`、`code:30002`、
   `data.engine:"external"`，页面**不白屏**。

**讲解词**：
> 这台机器上我没设 `DEEPSEEK_API_KEY`，所以现在看到的就是**降级态**。降级不是失败：分数照样写、
> 通知照样发、界面照样能用，只是引擎换成本地关键词，并且把「已降级」三个字画在卡片上。
> 库里这一行了得：`engine=LOCAL_KEYWORD`、`degraded_reason=EMPTY_KEY`，`latency_ms` 和两个 token 计数**是 NULL** ——
> 因为根本没发请求，不估算。降级原因一共七种，熔断打开也算一种，阈值是连续 5 次失败、冷却 5 分钟。
> 然后这里必须说一下两个链路的做法**不一样**：配对打分是异步的、可以降级；
> 而同步的 `/api/match` **不降级**。把装配值从 `local` 改成 `external`，容器里就没有引擎实现了，
> 接口直接 503、业务码 30002，不拿关键词分数去冒充模型分数。
> 理由有两个：静默降级会让「哪个引擎算出来的」这一列变脏，评估数据就废了；
> 对用户假称「这是模型算的结果」，比报错更糟。
> 刚才重启掉登录这件事，就是已知限制第 3 条：会话在内存里，没用 Redis，重启即失效。

**易错点**：
- 第 5 步要不要录，取决于时间。**只录前半（1–4）也是完整的降级演示**，省掉 20 秒。
- 千万别在录之前「顺手」把 Key 设上再录降级 —— 那就得重开机重启流程。
- 若按 `941fdee` 录：`/api/match` 的降级与否、`503/30002` 的行为**已在单测固定**
  （`MatchServiceTest#missingEngineBeanIsExplicit`），现场复现只是给观众看一眼。
- 讲完这段记得把环境变量清掉再录 S8，避免 S8 的取号演示在 external 环境里做（取号不依赖 match 引擎，
  但**详情页的匹配区会一直报 503**，画面上很干扰）。

### S8 · 缓存与审计回放（0:40）

**画面**：正常窗口（demo01，`/records/1` 详情）+ F12 Network + 终端 `mysql>`。

**操作**：

1. 先清掉屏幕上已显示的号码（刷新一次页面）；
2. 点「查看联系方式」，在 Network 里点开 `contact` 那条 → **Response Headers**：`Cache-Control: no-store`；
3. **再点一次**「查看联系方式」→ Network 里出现**第二条** `contact` 请求（不是缓存命中，不是 304）；
4. 按浏览器后退再前进（或切到别的详情页再回来），第三次点 —— 让观众看到「号码不会留在历史快照里」，每次都要重新取；
5. 终端查审计：
   ```sql
   SELECT id, pair_id, viewer_id, viewer_side, target_side, score, result, request_id, created_at
     FROM t_access_log ORDER BY id DESC LIMIT 6;
   ```
   **预期输出**：刚才每一次点击**各一行** `result=GRANTED`，`request_id` 各不相同，且与响应体里的 `requestId` 同值；
6. 用其中一个 `request_id` 反查一条链路（现场敲）：
   ```sql
   SELECT id, pair_id, viewer_id, result, ip, user_agent FROM t_access_log WHERE request_id = '<刚才那个 id>'\G
   ```
7. 最后给一句字段级取证：
   ```sql
   SHOW COLUMNS FROM t_access_log;
   ```
   数一下 11 列，并让观众看到**没有 `contact`、没有 `note`** 这两列。

**讲解词**：
> 取号这个接口带 `Cache-Control: no-store`。我连点三次，网络面板里就是三条真实请求 ——
> 中间没有任何一层能替我存这个号码，浏览器后退拿到的也不是缓存副本。
> 为什么这么较真：这一类响应是「谁的会话决定内容」的个性化数据，一旦被中间层按 URL 缓存，
> 就会把甲的号码回给乙，直接绕过鉴权和 404 门槛。
> 再看库里这张 `t_access_log`：三次点击三行，每行一个 `request_id`，和响应体里那个 `requestId` 是同一个值 ——
> 这就叫回放：拿着一个用户投诉或者一条响应，能从浏览器一路查到这一行 SQL。
> 最后一件事：这张表只有 11 列，里面**没有号码列、没有附言列**。审计记的是
> 「谁、在哪条配对、以哪一端、当时多少分、结果允许还是拒绝、什么 IP 与 UA、什么时候」，
> 不复副本人的手机号。授权可以撤回，被复制出去的号码收不回来。

**易错点**：
- `no-store` 在 `941fdee` 上只有 `GET /api/pairs/{id}/contact` 这一处（`PairController:66`）。
  **全站 `/api/**` 一律 `no-store`** 是 P2 加固分支 `fbd538f` 的行为，**尚未合入**：在基线上录，
  `GET /api/records` 的响应头里是没有 `Cache-Control` 的。所以本片只演取号那一条的头，不要顺手翻列表请求。
- 审计行是「每次查看一行」，不是「每人每对一行」。录之前 `t_access_log` 从 0 开始，讲解词里「三行」才对得上。

### 被追问时的两段标准答法

- **「你们的登录与权限做到什么程度？」**
  > 做。17 个业务接口里 **11 个必须登录**（8 个写 + 3 个私有读），门禁是一个排在 MVC 之前的过滤器，
  > 非 `GET/HEAD` 的 `/api/**` 一律先要会话，私有读登记了四条前缀：`/api/auth/me`、`/api/my`、
  > `/api/notifications`、`/api/pairs`；白名单只有登录、登出和运维扫描三个入口，
  > 将来新增写接口忘了登记也不会变成「匿名可写」——
  > 越权 403/`10007`，不可见 404/`20001` 且与「不存在」同码同文案。本期不做的是**角色体系/RBAC**、
  > 自助注册和密码找回。
- **「42% 那条为什么看不见？」**
  > 服务端不下发卡片，前端连数据都拿不到；我直接打接口拿到的是 403 + `50002`，审计写 `DENIED_LOW_SCORE`。
  > 门槛在服务端，前端隐藏只是体验。
