## 0. 一页 TL;DR

### 现在最值得改的三件事

1. **升级路径会丢数据，也交不出可执行的迁移**（P0-A）。
   部署包只带 `db/schema.sql` + `db/seed.sql`，不带 `db/migration/`；`DEPLOY-WINDOWS.md:616` 却让用户「用 schema.sql 里附带的 ALTER 语句」升级，而 `schema.sql` 的 `ALTER TABLE` 实测为 **0** 条、开头是 `DROP TABLE`。v2.0 用户在包内**没有一条正确的升级路径**；照文档猜下去就是删库。修法很小：迁移脚本打进包 + 重写 §10.1 + 补一次 v2.0→v2.1 演练。

2. **答辩材料与 main 是两套事实**（P0-B）。
   §5.9/§5.10/§6.13/§6.14 只在 94 的 **WIP 提交 `b0f7f81`**（标题写「草稿（未完成）」）里，main 一行都没有，`record-script-v2.md:620` 还在引用不存在的 §5.9；main 的设计文档仍写「7 张表 / 82 列 / 9 外键 / 23 CHECK / 17 业务接口 + 2 运维」，而 `d21081b` 实际是 **8 张物理表 / 117 列 / 29 CHECK / 10 外键 / 18 业务 + 3 运维 = 21 条路径**；`api-contract-v2.md` 对 `confirm-publish` / `ops/reviews` / `reviewState` **0 命中**；架构图仍写「九接口 / 三张表 / 无登录」，配对图仍是 0.75/0.90。评委只要 `SHOW TABLES` 或翻契约，就会当场对不上。

3. **发布闸门的两条确定性规则自相矛盾**（P1-1 + P1-2）。
   一是双检把「归一化变更」当成敏感命中：AI 输出只要有一个全角冒号（`时间：…`），四个字段任一命中就判 `REJECTED`，理由还写成「规则双检命中：手机号/证件号/邮箱/QQ」。二是双检和展示遮蔽都漏 `QQ 123 456`、`微信 abc-123456`。两条都可复现、修复都在 S 级，且都直接动摇「规则双检是唯一放行凭证」的答辩口径。

> 紧随其后的第 4—6 件：**编辑与审核并发时旧快照会覆盖新内容 / 让新内容走本人确认**（P1-3）；**DEGRADED「≤10 分钟恢复」与 60 分钟冷却矛盾**（P1-4/P1-5）；**本地 0.40 的「代价为零」被同一份校准数据证伪（负例 specificity 6/10）**（P1-6）。

### 最不值得改的三件事

1. **把 `program-design.md` / `v2-architecture.md` 里所有 `0.90/0.75` 旧示例逐条重写**。文档开头已有「口径更新」横幅，重写 30+ 处收益低、改错风险高；只把横幅里的 `0.45` 改成 `0.40` 即可（C-2）。
2. **为了 `MANUAL_APPROVE/MANUAL_REJECT` 两个历史枚举值单独做一次迁移**。代码里已无写入路径，不构成绕过；下次建库/迁移顺手清理即可（C-5）。
3. **收窄 CORS 的 loopback 通配、加 HTTPS、或引入 Flyway**。这些是单机演示的既定取舍（`WebConfig` 注释已说明代价），答辩前动它反而可能重现 8088 的 CORS 403，风险和收益不成比例。

### 一句话结论

**代码主路径比预期扎实**：审核闸门的状态机、三档取号与 fail-closed 审计、`is_visible` 单点可见性、会话换 id、启动脚本的 PID/端口保护都经得起追问，值得保留。真正会「交不出去 / 现场翻车」的是**交付与证据层**（升级、答辩材料数字、无 key 默认行为、QA 可复跑），加上**三处实现层的自相矛盾**（双检误拒、遮蔽漏检、编辑-审核竞态）。

## 3. 阻塞项（P0）

### P0-A · 阻塞 · 数据/交付：v2.0→v2.1 的升级路径不可执行，包内没有迁移脚本

**位置**

- `deploy/build-package.ps1:332-333`（只复制 `db\schema.sql`、`db\seed.sql`，没有 `db\migration\`）
- `deploy/DEPLOY-WINDOWS.md:616`（「数据库结构有变更时，用新包 `db\schema.sql` 里附带的 ALTER 语句手工执行」）
- `db/schema.sql:46-50`（以 `DROP TABLE` 开头；全文 `ALTER TABLE` 实测 **0** 条）
- `db/migration/v2.1-review-gate-up.sql:19`、`v2.1-review-gate-down.sql:12`（`USE \`find_it_campus\`;` 写死库名）

**现状**

v2.1 新增了 `t_record` 的 18 个列（`review_*` / `raw_*` / `match_*` / `summary` / `is_visible` 生成列等）与 `t_review_audit` 表。正确路径是仓库里的 `db/migration/v2.1-review-gate-up.sql` → `...owner-confirm-up.sql`。但：

1. 部署包**不带**这两个文件，用户在包内找不到迁移脚本；
2. 部署文档让用户去 `schema.sql` 找「附带的 ALTER」，而 `schema.sql` 是「空库全量重建」脚本（`DROP TABLE` 开头、0 条 ALTER），**不存在**这些 ALTER；
3. 迁移脚本自身把库名写死为 `find_it_campus`，而 `install.ps1` 支持 `-DbName`（`docs/testing/v2/v2.1.0-integration.md:37` 的真包验证就用 `findit_v210`），自定义库名时迁移会打到不存在的库或错库；

### P1-1 · 建议 · 正确性：规则双检把「归一化变更」误判为敏感命中，含全角冒号的合法文本会被终审拒绝

**位置**

- `server/src/main/java/com/findit/campus/review/postprocess/SensitiveTextScanner.java:69`
  `if (!MaskingPolicy.maskIdentity(text).equals(text)) { hits.add("手机号/证件号/邮箱/QQ"); }`
- `server/src/main/java/com/findit/campus/common/masking/MaskingPolicy.java:158-168`（`maskIdentity` 入口）
- `MaskingPolicy.java:408-421`（`normalizeDigitsAndColon`：无条件把 `：`→`:`、全角数字→ASCII）
- `server/src/main/java/com/findit/campus/review/service/ReviewGateService.java:139-145`（命中即 `REJECTED`，先于模型 decision）

**现状**

`maskIdentity` 的第一步是「全角数字/全角冒号归一」，这一步**总会在文本上留下差异**，即使没有任何号码被替换。扫描器把「整串是否变化」当成「是否命中敏感信息」，于是：

- `时间：昨天 14:30` → 命中「手机号/证件号/邮箱/QQ」（实际上只有全角冒号）；
- `摘要：黑色钱包` → 命中；
- `２０２６年１０月２１日` → 命中（全角数字）；
- `第三教学楼：三楼` → 命中；
- 同样的句子用半角冒号 `时间:昨天` → 不命中（对照组）。

**为什么是问题**

1. **误拒是终态**：`ReviewGateService.decide` 在模型 `decision` 之前先跑规则双检，命中直接 `REJECTED`（不重试）。AI 输出只要有一个中文冒号，这条启事就上不了架，用户只能改内容重发，而模型同样的改写很可能再次带冒号。
2. **理由误导**：拒绝理由固定为「规则双检命中：手机号/证件号/邮箱/QQ」，作者无法从理由判断是冒号造成的，会以为是模型把号码带出来了。
3. **与「规则双检是唯一放行凭证」的定位冲突**：放行凭证应该是「确定性命中」，不是「文本被归一化过」。
4. **测试没覆盖**：`SensitiveTextScannerTest` 只有 4 个用例，`noFalsePositiveOnNormalText` 用的是半角冒号；真包验证用的 stub 输出恰好不含全角冒号（`stub-llm.cjs` 的 APPROVE 文本是「黑色皮质钱包，图书馆三楼」），所以四条真包验证也没暴露。

**证据（harness 输出）**

```text
in=[时间：昨天 14:30]        hits=[手机号/证件号/邮箱/QQ]   masked=[时间:[时间已隐藏]]
in=[摘要：黑色钱包]          hits=[手机号/证件号/邮箱/QQ]   masked=[摘要:黑色钱包]
in=[物品：黑色皮质钱包，地点：图书馆三楼]
                             hits=[手机号/证件号/邮箱/QQ]
in=[２０２６年１０月２１日]  hits=[手机号/证件号/邮箱/QQ]   masked=[2026年10月21日]
in=[第三教学楼：三楼]        hits=[手机号/证件号/邮箱/QQ]
in=[时间:昨天 14:30]         hits=[]                        ← 半角冒号对照
```

**建议**

- 把「检测」与「替换」拆成两个能力：`MaskingPolicy.detectIdentity(text)` 返回命中的类别（或 `maskIdentity` 返回 `(masked, hit)`），扫描器用 `hit` 而不是整串 diff；这样归一化不再等于「命中」。
- 补 4—6 条单测：全角冒号、全角数字、全角冒号+真号码、半角冒号对照、中英混排，以及一条 `ReviewGateServiceTest`（模型输出带 `：` 时应 APPROVED）。

**工作量**：S（0.5—1h）
**影响答辩**：是。现场发布若模型输出带冒号，功能直接失败，且错误文案会把人引向错误方向。

### P1-2 · 建议 · 安全/隐私：QQ 分隔号码与微信 ID 在展示遮蔽和规则双检里都漏

**位置**

- `MaskingPolicy.java:57`：`QQ_RE = (?i)(QQ|扣扣|企鹅)\s*[:：号]?\s*(?<!\d)\d{5,9}(?!\d)` —— 只匹配**连续** 5—9 位。
- `MaskingPolicy.java:178-247`：分隔符归一（`maskSeparatedContactNumbers`）只处理 11 位手机号 / 18 位证件号（含 `+86/0086`），不处理 QQ。
- `IdentityScrubber.java:34-35`：`SOCIAL_LABEL = (?i)(微信|wechat|QQ|扣扣|企鹅)\s*[:：号]?\s*[A-Za-z0-9_-]{5,20}` —— **比对通道**会剥微信/QQ。

**实测**

| 输入 | `maskIdentity` | 扫描器 hits | 说明 |
|---|---|---|---|
| `QQ 123 456` | 原样 | `[]` | 数字被空格拆开，QQ_RE 不命中 |
| `QQ 123-456` | 原样 | `[]` | 短横同样 |
| `加我企鹅 123 456` | 原样 | `[]` | 关键词+分隔同样漏 |
| `微信 abc-123456` | 原样 | `[]` | 只有 SOCIAL_LABEL 管，展示层不认 |
| `QQ:123456789` | `QQ[QQ号已隐藏]` | 命中 | 连续数字正常 |
| `手机 138 1234 5678` | `[手机号已隐藏]` | 命中 | 手机号分隔归一已修好（F3 P1-1） |

**为什么是问题**

1. 展示文本来自 AI 改写。模型被要求删除联系方式，但它可能保留「QQ 123 456」这种自然写法；出口遮蔽不处理、规则双检也不命中，内容就进入公共列表/详情。
2. 项目对外的口径是「展示遮蔽单点实现」「规则双检是唯一放行凭证」。这两条漏检让「唯一」不成立；而**比对通道已经会剥微信/QQ**，说明规则集在两个通道分叉了。
3. 手机号分隔绕过（F3 P1-1）已经修复并复验通过，本条是**同类剩余面**，不是回归；但它恰好是任务书点名要看的 `QQ 123 456` 形态。

**建议**

- 把 `SOCIAL_LABEL`（微信/QQ/wechat）提升为 `MaskingPolicy` 的第五条规则，展示层与双检共用；
- 或者让 `maskSeparatedContactNumbers` 对「关键词 + 任意分隔符 + 5—9 位数字」的片段做归一，命中后替换原文整段（与手机号同一套扫描器）；
- 补 4 条用例：QQ 空格、QQ 短横、QQ 全角空格、微信字母数字 ID；同时补 `SensitiveTextScanner` 回归断言。

**工作量**：S（1—2h）
**影响答辩**：可能。被问「分隔符绕过全修了吗」时，目前只能答「手机号修了，QQ/微信还有口子」；如果先修，这题是加分项。

### P1-3 · 建议 · 并发/数据：编辑与审核并发时缺少内容版本，旧审核快照会覆盖新内容或让新内容走本人确认

**位置**

- `ReviewGateService.java:73` 只读一次 `record` 快照；`:85-119` 用它重试、`decide(record, last)`、最后 `approve/reject/markOwnerConfirmRequired`。
- `RecordMapper.xml:263-294`（`updateContent`）：编辑把 `review_state` 重置 PENDING、`review_manual_required=0`、`review_attempts=0`，**但没有任何版本号/内容 hash 列**。
- `RecordMapper.xml:460-477`（`approveReview`）：写入 `title/description/location/summary`，`WHERE id AND deleted_at IS NULL AND review_state='PENDING'` —— 不校验内容版本。
- `RecordMapper.xml:500-510`（`markOwnerConfirmRequired`）：`WHERE ... review_state='PENDING'`；`:533-543`（`confirmOwnerReview`）：`WHERE ... review_state='PENDING' AND review_manual_required=1`。

**现状（代码级序列）**

```text
T1 发布（内容 A）→ PENDING，异步审核开始，ReviewGateService 加载 A 的快照
T2 作者编辑（内容 B）→ updateContent 把 B 写成展示/比对文本，review_state=PENDING、manual=0
T3 旧审核线程完成：
   3a 若 APPROVE → approveReview 用 A 的 title/description/location/summary 覆盖 B
      （WHERE 只看 review_state=PENDING，会命中），B 的展示文本被静默回退；
   3b 若 4 次失败 → markOwnerConfirmRequired 把 manual=1 写到 B 上，
      作者随后 confirm-publish 会把 **B**（未经 AI 泛化）上架，审计却记的是对 A 的审核失败。
```

**为什么是问题**

- 结果是用户编辑被静默回退（3a），或审核闸门对「未经 AI 审核的新内容」开了一条本人确认的路（3b）。后者不是「作者越权」（作者本来就能确认自己的内容），而是**审计与闸门语义被破坏**：`review_state` 只说「这一行在等审」，没有说「审的是哪一版内容」。
- `updateContent` 的注释明确写「旧结论不能复用在新内容上」，但缺版本号，这个承诺在**并发窗口**里不成立。
- 窗口不小：AI 审核 4 次调用 + 1s/2s/4s 退避，最长约 22s；编辑页对 PENDING 记录是开放的（`RecordEdit` 只在 `status != PENDING` 时禁止）。

**证据**

- 代码路径如上（`ReviewGateService.java:73-119` + `RecordMapper.xml:263-294/460-477/500-510`）。
- **未做真实并发复现**（没有起服务/库）；这是代码级序列推断。验证方法：用 `Thread.sleep` 在 `PostprocessClient` 里制造 10s 延迟，发布后在另一请求 PUT 新内容，观察 `t_record.title` 是 A 还是 B、`review_manual_required` 是否变成 1。

**建议**

- 加 `content_version INT NOT NULL DEFAULT 0`（或复用 `updated_at` + 内容 hash）：
  - `updateContent` 时 `content_version = content_version + 1`；
  - `process()` 加载快照时带版本；`approveReview/rejectReview/markOwnerConfirmRequired` 的 WHERE 加 `AND content_version = #{expectedVersion}`，命中 0 行就放弃本轮（让新内容重新审核）；
- 或者最简：编辑时如果 `review_state=PENDING` 且 `review_attempts>0`，返回 409「审核中，请稍后再改」——但这会牺牲编辑体验，推荐版本号。
- 补一条并发测试（可用可控延迟的 fake client）。

**工作量**：M（迁移 1 列 + 4 条 SQL + 测试）
**影响答辩**：是（「编辑后重新审」是 §5.9 的必答点；被追问并发时当前答不圆）。
