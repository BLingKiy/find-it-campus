# 四人答辩讲稿（约 10 分钟）

> A / B / C / D 换成各自名字。全文约 2500 汉字，按每分钟 230–250 字估算，正常语速 9–10 分钟。
> 页码对应 `答辩PPT.pptx`，讲的时候以内容为准，不必严格按页序。

## A · 架构、数据库与主文档（约 3 分半）

【开场】

各位老师好，我们是 find-it-campus 小组。我们做的是校园失物招领平台，一句话说清它干什么：让丢东西的人和捡到东西的人，在不公开彼此联系方式的前提下，尽快找到对方。下面四个人分别讲自己负责的那块，我先说架构、数据库和主文档。

【问题与架构】

校园里的失物信息现在散在微信群、表白墙和公告板上，有三个很具体的毛病。一个是找不到，一条消息发出去，很快被后面几十条冲走；一个是分不清，"捡到一个黑色水杯"和"丢了一个黑色水杯"到底是不是同一件，只能靠人眼比对；还有一个是不敢留联系方式，留了手机号所有人都能看到，不留又没法认领。我们对应做了三件事：结构化发布、自动配对打分、按分数分档给联系方式。

架构选的是模块化单体。后端 Spring Boot 3 加 MyBatis，前端 Vue 3 加 Vite 加 TypeScript，数据库 MySQL 8，按层分包、依赖单向，部署就是一个进程，验证成本最低。common 层做四件横切的事：统一响应体、错误码映射、会话门禁、输出遮蔽，这四件事都只允许一处实现。接口是 17 个业务加 2 个运维，一套外壳；权限矩阵 17 乘 3 共 51 格，每格都有状态码，不是"大概允许"。错误码按 HTTP 状态、业务 code、message 三段式。这里踩过一个坑：契约里写数据库不可用返回 503，代码默认映射成 500，最后统一成 500，由健康检查在返回时显式覆写 503，两轨不同源，但口径写死了。

【数据库】

数据库这块我做的是表职责划分、约束下沉和索引。7 张表、82 列、9 条外键、23 个 CHECK。核心两张：t_record 一张表同时放寻物和招领，用 type 区分；t_pair_score 一行就是一对寻物和招领，唯一键是 lost_id 加 found_id，一条招领可以和多条寻物各成一对，处理完一对不影响别的对。审计表 t_access_log 只插不改不删，没有号码列，它只回答谁在什么时候看了哪一对、结果如何。23 个 CHECK 是把靠约定维持的规则交给数据库兜住，比如两个确认时间必须同时有值，才等于 MATCHED。种子数据做成幂等的，重复导入不会翻倍。索引按查询路径配：列表和召回各走自己的索引，发布量上来以后不会互相拖慢。

【主文档】

主文档是我牵头写的，10 章加两个附录：需求、架构、七张表、接口、匹配、实现、测试、限制，附录 A 是接口清单，附录 B 是文档和代码的逐条核对记录。文档里的每个字段名、接口路径、状态码，都能回到源码行或者一条测试输出。docx 是脚本从 Markdown 导出的，源和导出件一起提交，改文案只改源文件。

架构、数据和文档大概这些，前端怎么接，交给 B。

## B · 前端（约 2 分钟）

【主流程】

我负责前端。技术栈是 Vue 3 加 Vite 加 TypeScript，页面是三页主流程——列表、详情、发布，加上登录、我的启事、通知。身份只有三种：匿名、本人、非本人，所有页面的可见性都按这三种算，不另造角色。列表页负责检索和筛选；详情页是核心，配对卡片按三档渲染；发布页选寻物还是招领，填标题、描述、地点、分类。

【三档交互】

三档落到界面上是这样：DIRECT 直接显示号码；AUTHORIZABLE 显示"申请授权"，对方同意之后才出号；LOW 连卡片都不生成。授权两端是独立的，我点授权只代表我这一端公开，对方撤不撤回跟我这边没关系；撤回也做了，撤完马上恢复遮蔽，不用等刷新。取号失败时，界面不会先把号码闪一下再报错——后端是先落审计再出号，写不进审计就不给号，前端只按结果渲染。待审记录的"确认发布"入口也一样，以服务端返回的 ownerConfirmAvailable 为准；AI 审核正常时这个字段是 false，页面根本不渲染，避免用户看到一个点了会 409 的按钮。

【状态与细节】

错误处理做了统一映射：401 跳登录，403 和 404 分开提示，字段级错误回到对应输入框，不弹一句"操作失败"了事。空态、加载态、过期记录也都单独处理，比如已完成的记录在公共列表里消失，但本人还能在"我的启事"里看到。UI 基线把颜色对比度、按钮圆角、间距、表单控件统一成一套 token，白字在品牌色上的对比度至少 6.7 比 1，不每个页面各写各的。路由守卫在进页面前判登录态，未登录带着原路径去登录，登录后回原页面；三页的组件和表单控件复用同一套，样式只维护一份。

前端大概这些，后端怎么实现，交给 C。

## C · 后端（约 3 分钟）

【接口与登录】

我负责后端。17 个业务接口加 2 个运维接口都在这里落地，登录只认服务端会话，AuthGateFilter 挂在 DispatcherServlet 前面，规则是"非 GET 和 HEAD 的 /api 一律要登录"，例外只有 login、logout、运维扫描三条。所有响应走同一套外壳，错误码在 common 层统一映射，业务代码里不各拼各的 JSON。

【遮蔽与三档】

隐私这条线，遮蔽只在输出层做一次，五个出口共用同一套规则；原文只给本人，比对文本只剥身份信息，展示文本全脱敏。联系方式按分数分三档：语义引擎 0.95 以上直接给号，0.80 到 0.95 要对方授权，0.80 以下不出卡片；本地引擎分数量纲不一样，用 0.90 和 0.40。阈值是拿 20 对标注样本校准出来的，不是拍脑袋。取号之前先写审计，写不进审计就不出号。会话是 HttpOnly Cookie，30 分钟失效，口令用 bcrypt 存；配对成功和授权时会写通知，标题和正文入库前已经打过码。

【配对链路】

配对是发布之后异步跑的。发布事务提交以后再发事件，用独立线程池，不占发布请求——实测发布接口 0.05 到 0.17 秒，模型再慢也拖不住用户。召回先用本地关键词把整池预排，取前 N 条，再逐对调 DeepSeek 打分；内容哈希没变就跳过，不重复计费。幂等靠三层：数据库唯一键、内容哈希、MySQL 命名锁，两个入口同时算同一对，最后也只会落一行。命名锁是会话级的，所以锁的生命周期绑在同一条连接上，避免锁永远不释放。

【降级与审核】

AI 这块，匹配能力收在 MatchEngine 接口后面，密钥只从环境变量读，配置文件里没有 key 字段。七种降级原因都落库，模型挂了就用本地关键词分顶上，界面会明说"已降级"。/api/match 这个即时匹配接口直接 503 或 504，不偷偷换算法；发布后的配对链路降级出分，因为用户等的是后台结果。熔断是三态，模型恢复后 10 分钟重扫降级记录，冷却 60 分钟，重算只更新分数那几列，不碰状态，也不撤销已经解锁的联系方式。审核闸门是发布先落库、异步审核，默认走 AI，失败三次转本人确认；AI 正常的时候，那个确认入口前端不渲染。删除记录会清掉原文并写一条审计。

后端大概这些，测试和 PPT 交给 D。

## D · 测试与 PPT（约 2 分钟）

【测试】

我负责测试和答辩 PPT。测试有四套回归：接口 111 条、前端 E2E 25 条、跨页一致性 9 条、落库取证 19 条，后端单测 242 条。另外做了 28 个手机号泄漏探针，覆盖匿名、非本人、通知正文这些出口，最后是 0 命中。安全复核那边 P0 是 0，P1 的遮蔽绕过修了，P2 四项也做了修复和复验。

【踩过的坑】

测试不是为了凑数。第一轮接口是 63 过 1 挂，E2E 是 18 过 1 挂：一个非法日期返回 500，契约要求 400；一个重置筛选后 URL 残留参数。修完按原断言原样复跑，没有放宽门槛。另外两个 P2 也修了：非法 JSON 时字段错误列表为空、先翻页再重置页码不回退。单测一开始是 17 条全红，基线本身跑不过，最后补到 242 条全绿。每次修完，我都会把修复前的失败输出和修复后的通过输出一起归档，答辩时被问到，可以直接翻出来。回归入口是一条命令 node qa/run-all.mjs，报告按日期归档，换台机器也能复跑。

【PPT】

PPT 26 页，内容源是一份 Markdown，构建脚本生成 pptx，改文案只改源文件。整片的顺序是：问题、范围、架构、数据、接口、四个新增能力、匹配链路、测试、开发过程、分工。每一页上的数字，都能在设计文档或测试报告里指到出处；没有"大概""差不多"这种词。分工页按四个人各自的主责域写，谁负责哪几章、交付了哪些东西，都对应到具体章节和 commit。

最后一句：这个项目我们最在意的是，每个说"完成了"的地方，都能在仓库里找到一个文件、一条测试输出对上。就这些，谢谢老师。
