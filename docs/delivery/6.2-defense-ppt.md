# 选题：问题不在「没有平台」，在「信息不聚合」
- 现状三条渠道：微信群、表白墙、宿舍楼下纸质启事
  - 失主在群里刷屏询问，招领信息却在另一个群
  - 纸片启事只在原地可见，跨校区无效
  - 即使两边都发了，也没有任何机制把「丢了黑钱包」和「捡到黑钱包」连起来
- 结果：最该发生的匹配，靠运气
- 本项目把这条链路做成可运行的系统：发布 → 检索 → 按描述语义找匹配 → 走完状态流转

> 我们做的不是「再一个信息发布页」，是「让两条本来碰不上的启事发生关系」。

# 选题难度：难在四个约束必须同时成立
- **三张表是硬上限**：每张表都要承担复合职责 —— `t_record` 一表两用（寻物/招领）、`t_category` 兼作匹配词表、`t_match_result` 既是评估证据又能反查候选
- **契约先行 + 前后端并行**：接口契约是唯一事实源，DB `snake_case` 与 JSON `camelCase` 两侧命名不同，错误码要双轨表达
- **AI 匹配必须可替换**：评分看的不是「用了 AI」，是「能不能把 AI 换掉而调用方不动」
- **无登录体系下的边界设计**：写接口对访客开放是已声明的取舍，靠逻辑删除、状态机收口、前端 pending 禁用缓解

> 难度不是技术栈堆得多，是「约束交叉时还能跑通」。

# 接口设计：九个接口，一套外壳
| # | 方法与路径 | 用途 | 主要错误码 |
|---|---|---|---|
| 1 | `GET /api/health` | 健康检查（DB 状态、引擎名） | 10005 |
| 2–7 | `/api/records` 增删改查与状态流转 | 列表、详情、提交、全量修改、状态、逻辑删除 | 10001、20001、20002、20003 |
| 8 | `GET /api/categories` | 分类字典（只返启用，按序） | — |
| 9 | `POST /api/match` | 语义匹配：描述 → 候选 + 相似度 | 30001、30002、30003、40001 |

- 统一外壳四个字段：`code` / `message` / `data` / `requestId`，含 404 与 405
- 13 个错误码 + 成功码 0：HTTP 状态由 `ErrorCode` 单一映射，业务分支只看 `code`（4xx 归用户、5xx 归系统）
- 详情出参带 `allowedStatuses`：状态机放后端，前端不自己推按钮
- 校验失败 `fieldErrors` 一次返回**全部**违规字段，前端一次性标红
<!-- note: 至少 60 秒。九接口不要逐个念。讲三件事：外壳唯一、错误双轨、allowedStatuses 让前端零流转知识。这三件是「工程规范」的实证。 -->

# AI 匹配亮点一：三条边界把「接口独立」做实
| 边界规则 | 具体约束 | 挡住的变化 |
|---|---|---|
| **引擎不碰数据库** | 不注入 Mapper、不写库，只消费调用方递进来的候选池 | 换实现不必理解表结构；外部实现可单测覆盖，不用起库 |
| **引擎只返回 `recordId + score + reason`** | 展示字段由 service 回表补齐 | 可见性规则只存在一处，不被每个算法各实现一遍 |
| **引擎不知道 HTTP** | 没有 `HttpStatus`、不接收 DTO，异常只有 `MatchEngineException` | 引擎可被任何入口复用，不背 HTTP 概念 |

- 候选池由 `MatchService` 递入，而不是引擎自己去取 —— 这一条决定了「换实现」的工作量
- 额外两个好处：外部实现可以被单测覆盖（无需起库）；删掉的记录由回表过滤吸收，前端不会看到死链

> 「接口独立」不是画在图上的一句话，是这三条约束，且每一条都能在源码里指到对应位置。
<!-- note: 90 秒。这一页是技术先进性 20 分的一半。要说透「候选池为什么由调用方给」：如果引擎自己查库，换实现就得把可见性规则再实现一遍。 -->

# AI 匹配亮点二：可替换是测试固定的事实
- 切换方式是**一个配置值**：`findit.match.engine=local|external`，容器里恒只有一个 `MatchEngine` bean
- 不做自动回退：外部挂了就是 503，不悄悄用关键词分数顶上 —— 静默降级会污染 `impl` 列
- `KeywordEngineSwappabilityTest` 在**同一调用点**注入 Fake 实现与真实实现，断言两者都满足契约（≤ `topN`、≥ `minScore`、去重、降序、`score ∈ [0,1]`）
- 3.2 交付时 `MatchService` 与 `MatchController` **零 diff** —— 可替换不是承诺，是被测试固定住的事实
- 本期口径：只认「本地实现 + 文档化替换路径」，外部实现另立任务，**未落地**
- 换实现的改动面：

| 变更 | 需要改 | 不需要改 |
|---|---|---|
| 本地 → 外部 | `application.yml`、新增 `ExternalEmbeddingMatchEngine`、`MatchEngineConfig` 一个 `@Bean`、必要时加 `impl` 枚举值 | `MatchEngine` / `MatchQuery` / `MatchService` / `MatchController` / 请求响应 DTO / 前端**全部代码** |
<!-- note: 90 秒。重点讲最后一行的诚实边界：我们没做外部实现，但我们证明了换实现不用动调用方。评委问「那你到底有没有 AI」——答：有本地打分实现，向量模型是计划中的替换路径，接口已经把它预留好了。 -->

# 开发过程：一人项目，多 Agent 流水线
- 八个角色分阶段交付：需求 → 架构 → 后端 → AI → 前端 → UI → 测试 → 文档，人只做两件事：**拍板**与**合并 `main`**
- 分支模型：功能分支 `feat/<阶段>-<主题>` → 各 Agent 的 `hifox-agent/<名>/<任务号>` → 集成分支 → `main`（仅人类合并）
- 验收方式是**看证据不看自述**：每条交付评论必须带分支名 + commit SHA + 实测输出 + 附件，验收方 `git ls-remote` 核对 SHA、下载附件抽查、必要时本机重跑
- 时间线：10-21 19:50 初始化 → 23:37 前后端骨架 → 10-22 11:42 九接口 → 12:01 匹配引擎 → 14:23 集成 → 15:13 测试收口 → 10-26 09:14 `main` 合入 `d38f868` → 10-26 11:17 三条分支合入 `main`（`821423e` / `a7abde6` / `baf9e44`）
- 交付物的可核对性来自这条链：commit → 任务评论 → 测试输出 → 文档，任一环断掉就重做

> 这也是「文档与视频 30 分」的实质：不是材料做得多，是每条结论都能回溯到某个时点的证据。

# 开发过程：四个真实踩过的坑
| 编号 | 现象 | 处置与教训 |
|---|---|---|
| P-02 | 同一个错误码 `10005` 在三处文档/代码里互相矛盾（500 / 503 / 待确认） | 人类拍板固定枚举 500，DB 不可用由 `HealthController` 显式覆写 503；教训是「规范自身没闭合」比实现写错更常见 |

# 已知不足与后续毕设方向
- **匹配只做关键词**，不是语义理解：同义词、拼音、脱离词表的近义表达无效（实测：`丢了一个水杯` 空结果、`tushuguan diu le qianbao` 空结果）
  - 改造路径：新增 `ExternalEmbeddingMatchEngine` + `engine=external`，前端与契约零改动（已测试固定）
- **没有登录与权限**：写接口对访客开放、联系方式任何人可见、重复提交无法去重 —— 毕设加鉴权与数据归属后，这三条同时收敛
- **没有图片上传**：失物信息里图片的价值极高，需引入对象存储，属于第 4 张表以外的独立演进
